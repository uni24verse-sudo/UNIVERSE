A. Why We Do Not Store Student Passwords

  • Traditional websites store thousands of student passwords, making them targets for hacking.
  • UniVerse eliminates this risk entirely: students do not create password accounts.
  • Active order tracking uses secure client-side tokens stored only in the student's browser. Even in the theoretical case of a database breach, there are zero student passwords to leak.

B. What Information We Collect vs. What We NEVER Collect

  • Information We Collect:
    • First Name: Displayed on kitchen screens so cafeteria staff can call out the tray.
    • WhatsApp Phone Number: Used solely to send real-time order readiness alerts and digital receipts.
  • Information We NEVER Collect:
    • Student passwords, roll numbers, hostel room numbers, parent contact info, national IDs (Aadhaar/PAN), or background GPS location.

3. Payment Security & Financial Compliance (PCI-DSS & RBI)

The university and its vendors carry zero financial or cardholder liability:

  • 100% Payment Gateway Offloading: All digital payments (UPI, Google Pay, PhonePe, Paytm, Debit/Credit cards) are processed on Razorpay's PCI-DSS Level 1 certified banking infrastructure.
  • Zero Card Storage: UniVerse servers never receive, store, or transmit raw credit card numbers, CVVs, or UPI PINs.
  • Cryptographic Webhook Verification (HMAC-SHA256): Payment confirmations from the gateway are cryptographically verified using secret HMAC signatures. Unpaid or forged orders are blocked immediately.
  • Automated Instant Refunds: If a vendor kitchen runs out of stock, the system automatically triggers an instant refund API call back to the student's UPI/bank account with an immediate WhatsApp confirmation.

4. Physical Counter Security: Cryptographic Anti-Theft QR Handover

On crowded university campuses, food theft and confusion at the counter (e.g., someone picking up another student's tray) is a common issue. UniVerse solves this with single-use cryptographic QR handover:

│                 HOW THE ANTI-THEFT HANDOVER PREVENTS FRAUD                  │
└─────────────────────────────────────────────────────────────────────────────┘

  Student Smartphone                                 Kitchen Vendor POS
         │                                                   │
         │ ──── (Food is being cooked in kitchen) ────────── │
         │                                                   │
         │ ◄─── Kitchen clicks "Ready" ───────────────────── │
         │      (Server generates secret `handoverToken`)   │
         │                                                   │
         │ ──── Presents Single-Use Handover QR Code ──────► │
         │                                                   │
         │                                                   ▼
         │                                      [ Scanner / PIN Entry ]
         │                                                   │
         │                                                   ▼
         │                                      [ Atomic Database Check ]
         │                                      • Checks `handoverTokenUsedAt == null`
         │                                      • Marks `status = Completed` in 1 Op
         │                                                   │
         │ ◄─── Food Handed Over & Logged ─────────────────── │

How It Protects the University & Students:

  1. No Early Tokens: The handover token does not exist while food is being cooked; it is generated only when the vendor marks the food Ready.
  2. Single-Use Atomic Consumption: The QR code is permanently consumed in a single atomic database operation upon scanning.
  3. Screenshot Protection: If a student screenshots the QR code and shares it, the first scan completes the order. A second scan instantly returns an HTTP 409 Conflict: Order already handed over.

5. Network Security & Campus Wi-Fi Protection

  • End-to-End TLS 1.3 Encryption: All data transmitted between students, vendors, and servers uses strict HTTPS with 256-bit AES encryption. Packet sniffing or eavesdropping over open campus Wi-Fi is mathematically impossible.
  • VPC & IP Whitelisting: The central database (MongoDB Atlas Dedicated Tier) is isolated in a private cloud VPC and rejects all incoming connections except from authorized application servers.
  • Real-Time WebSocket Isolation: Kitchen screens use segregated WebSocket channels (storeId room isolation), ensuring Vendor A can never see orders or customer details from Vendor B.

7. High Availability & Lunch-Rush Reliability

Campus food ordering experiences extreme traffic concentration (hundreds of simultaneous orders between 12:00 PM and 2:00 PM). UniVerse is architected for zero downtime:

  • 3-Node Multi-Zone Database Replica Set: Data is continuously replicated across 3 separate physical availability zones. If one server experiences a hardware failure, an automatic failover occurs in under 2 seconds with zero data loss.
  • Point-in-Time Recovery (PITR): Continuous transaction logs and daily automated snapshots allow restoring the system to any precise second within the preceding 7 days.
  • Decoupled Microservices: The frontend, backend API, WebSocket engine, and database run independently. A traffic surge in messaging or analytics never interrupts food ordering or payment processing.
